# Excalidraw Diagram Creator

Generate `.excalidraw` JSON files that **argue visually**, not just display information.

**Setup:** If the user asks you to set up this skill (renderer, dependencies, etc.), see `README.md` for instructions.

## Customization

**All colors and brand-specific styles live in one file:** [references/color-palette.md](references/color-palette.md). Read it before generating any diagram and use it as the single source of truth for all color choices - shape fills, strokes, text colors, evidence artifact backgrounds, everything.

To make this skill produce diagrams in your own brand style, edit `color-palette.md`. Everything else in this file is universal design methodology and Excalidraw best practices.

---

## Core Philosophy

**Diagrams should ARGUE, not DISPLAY.**

A diagram isn't formatted text. It's a visual argument that shows relationships, causality, and flow that words alone can't express. The shape should BE the meaning.

**The Isomorphism Test**: If you removed all text, would the structure alone communicate the concept? If not, redesign.

**The Education Test**: Could someone learn something concrete from this diagram, or does it just label boxes? A good diagram teaches - it shows actual formats, real event names, concrete examples.

## Depth Assessment (Do This First)

Before designing, this skill works in one of four modes: **System Block Model**
(architecture, systems, pipelines), **C4** (architecture across explicit abstraction
levels), **Simple/Conceptual** (abstract mental models), or **Comprehensive/Technical**
(protocols, APIs, data formats, tutorials). Picking the wrong mode isn't a styling choice -
it changes the layout, the element budget, and whether evidence artifacts belong on the
page at all.

The full criteria for which mode applies, and the reference file each one reads before
laying anything out, live in **Design Process, Step 1** below - read there, not here, so
the rules exist in exactly one place.

One line so the wrong default never gets built: for architecture/system/pipeline
requests, **big blocks, nested containers, lots of whitespace - not a dense
multi-column map.** Swim-lane columns of labelled boxes are a table drawn with
rectangles, rejected as unreadable.

---

## Research Mandate (For Technical Diagrams)

**Before drawing anything technical, research the actual specifications.**

If you're diagramming a protocol, API, or framework:
1. Look up the actual JSON/data formats
2. Find the real event names, method names, or API endpoints
3. Understand how the pieces actually connect
4. Use real terminology, not generic placeholders

Bad: "Protocol" → "Frontend"
Good: "AG-UI streams events (RUN_STARTED, STATE_DELTA, A2UI_UPDATE)" → "CopilotKit renders via createA2UIMessageRenderer()"

**Research makes diagrams accurate AND educational.**

## Technical Diagram Depth (Evidence & Multi-Zoom)

For Comprehensive/Technical diagrams, read [references/technical-diagrams.md](references/technical-diagrams.md) before drawing: it covers evidence artifacts (code snippets, JSON examples, timelines), the three-level multi-zoom structure (summary / sections / detail), and a side-by-side of displaying vs arguing. Skip it entirely for System Block Model or C4 - evidence insets are an antipattern in both.

## Container vs. Free-Floating Text

**Not every piece of text needs a shape around it.** Default to free-floating text. Add containers only when they serve a purpose.

| Use a Container When... | Use Free-Floating Text When... |
|------------------------|-------------------------------|
| It's the focal point of a section | It's a label or description |
| It needs visual grouping with other elements | It's supporting detail or metadata |
| Arrows need to connect to it | It describes something nearby |
| The shape itself carries meaning (decision diamond, etc.) | Typography alone creates sufficient hierarchy |
| It represents a distinct "thing" in the system | It's a section title, subtitle, or annotation |

**Typography as hierarchy**: Use font size, weight, and color to create visual hierarchy without boxes. A 28px title doesn't need a rectangle around it.

**The container test**: For each boxed element, ask "Would this work as free-floating text?" If yes, remove the container.

## Design Process (Do This BEFORE Generating JSON)

### Step 0: Choose the Notation (MANDATORY)

Before anything else - before assessing depth, before reading any reference file - ask
the user which notation this diagram should use, with the options spelled out so they
only need to pick one:

- **C4** - explaining a system to people outside the team, at explicit levels of detail
- **System Block Model** - an internal one-sheet architecture, left-to-right flow
- **Data flow diagram** - what data moves and where it's stored
- **Sequence diagram** - order over time, who calls whom
- **Deployment diagram** - what runs on which machine, in which network

Do not silently pick a notation from keywords in the request and start drawing - that is
exactly what produced three full redraws of the same system in one real session, burning
roughly 2.8M subagent tokens and ninety minutes. **A wrong notation is not a fix, it's a
full redraw**, because sheet count, shapes, labels, and which connections are even legal
to draw all follow from the notation. The one exception: the user already named the
notation themselves in the request ("draw this as C4", "give me a sequence diagram") -
then proceed without asking again.

### Step 1: Assess Depth Required
Once the notation is settled, determine which of this skill's modes applies:

- **System Block Model**: architecture, system, pipeline - big blocks, nested containers,
  whitespace. Read [references/system-block-model.md](references/system-block-model.md)
  and open one of the reference PNGs it names before laying anything out. Do not start
  from the patterns in Step 4 - the canon layout in that file replaces them.
- **C4**: the user picked C4 in Step 0. Read [references/c4-model.md](references/c4-model.md) -
  four levels, one-sheet-per-level-per-container, sheet layout for a set, its own
  notation. Do not mix System Block Model patterns into it.
- **Simple/Conceptual**: Abstract shapes, labels, relationships (mental models,
  philosophies).
- **Comprehensive/Technical**: Concrete examples, code snippets, real data (protocols,
  data formats, tutorials) - **not** a system architecture, which belongs to System
  Block Model or C4 above. Do research first (see Research Mandate above), then read
  [references/technical-diagrams.md](references/technical-diagrams.md) for evidence
  artifacts and multi-zoom structure.

System Block Model and C4 both override Comprehensive/Technical: a dense information map
with evidence insets is wrong for an architecture request regardless of how much research
backs it.

### Step 2: Understand Deeply
Read the content. For each concept, ask:
- What does this concept **DO**? (not what IS it)
- What relationships exist between concepts?
- What's the core transformation or flow?
- **What would someone need to SEE to understand this?** (not just read about)

### Step 3: Build the Source Registry (When Drawing From an Existing Source)

When the diagram redraws something that already exists - someone else's diagram, a
design doc, a codebase - write out a numbered registry of the source's nodes and
connections as its own file, before drawing anything. The registry fixes what the source
actually contains; it does not get edited to match decisions made while drawing. Any
discrepancy (a decision to add, drop, or reinterpret something) is a note next to the
fact, with who decided and when - not a silent overwrite.

This is what makes coverage checkable later: without a numbered list of connections, no
one can say "connection 27 isn't drawn anywhere" - there's nothing to count against. Put
the file next to the target `.excalidraw` (same task working directory), not in a scratch
or temp location - it's a lasting artifact for the reviewer and any later session, not an
intermediate file to delete once drawing is done.

Skip this step only for a diagram built from a concept in your own head, with no
external source to reconcile against.

### Step 4: Map Concepts to Patterns
For each concept, find the visual pattern that mirrors its behavior:

| If the concept... | Use this pattern |
|-------------------|------------------|
| Spawns multiple outputs | **Fan-out** (radial arrows from center) |
| Combines inputs into one | **Convergence** (funnel, arrows merging) |
| Has hierarchy/nesting | **Tree** (lines + free-floating text) |
| Is a sequence of steps | **Timeline** (line + dots + free-floating labels) |
| Loops or improves continuously | **Spiral/Cycle** (arrow returning to start) |
| Is an abstract state or context | **Cloud** (overlapping ellipses) |
| Transforms input to output | **Assembly line** (before → process → after) |
| Compares two things | **Side-by-side** (parallel with contrast) |
| Separates into phases | **Gap/Break** (visual separation between sections) |

Once you've picked the patterns, read [references/visual-patterns.md](references/visual-patterns.md) for what each one
actually looks like, which shape (or none) each concept type takes, and the layout rules for
sizing and spacing them.

**System Block Model and C4 skip this table.** Their layouts are fixed by the canon in
`references/system-block-model.md` and `references/c4-model.md` respectively. Do not mix
fan-outs, clouds and timelines into either.

### Step 5: Ensure Variety
For multi-concept diagrams: **each major concept must use a different visual pattern**. No uniform cards or grids.

Exception: in System Block Model and C4, uniformity is correct - phase containers and
sibling components deliberately look alike so the eye reads the structure, not the
shapes. Variety there produces noise.

### Step 6: Sketch the Flow
Before JSON, mentally trace how the eye moves through the diagram. There should be a clear visual story.

### Step 7: Generate JSON
Only now create the Excalidraw elements. **See below for how to handle large diagrams.**

### Step 8: Render & Validate (MANDATORY)
After generating the JSON, you MUST run the render-view-fix loop until the diagram looks right. This is not optional - see the **Render & Validate** section below for the full process.

## Large / Comprehensive Diagram Strategy

**For comprehensive or technical diagrams, you MUST build the JSON one section at a time.** Do NOT attempt to generate the entire file in a single pass. This is a hard constraint - Claude Code has a ~32,000 token output limit per response, and a comprehensive diagram easily exceeds that in one shot. Even if it didn't, generating everything at once leads to worse quality. Section-by-section is better in every way.

### The Section-by-Section Workflow

**Phase 1: Build each section**

1. **Create the base file** with the JSON wrapper (`type`, `version`, `appState`, `files`) and the first section of elements.
2. **Add one section per edit.** Each section gets its own dedicated pass - take your time with it. Think carefully about the layout, spacing, and how this section connects to what's already there.
3. **Use descriptive string IDs** (e.g., `"trigger_rect"`, `"arrow_fan_left"`) so cross-section references are readable.
4. **Namespace seeds by section** (e.g., section 1 uses 100xxx, section 2 uses 200xxx) to avoid collisions.
5. **Update cross-section bindings** as you go. When a new section's element needs to bind to an element from a previous section (e.g., an arrow connecting sections), edit the earlier element's `boundElements` array at the same time.

**Phase 2: Review the whole**

After all sections are in place, read through the complete JSON and check:
- Are cross-section arrows bound correctly on both ends?
- Is the overall spacing balanced, or are some sections cramped while others have too much whitespace?
- Do IDs and bindings all reference elements that actually exist?

Fix any alignment or binding issues before rendering.

**Phase 3: Render & validate**

Now run the render-view-fix loop from the Render & Validate section. This is where you'll catch visual issues that aren't obvious from JSON - overlaps, clipping, imbalanced composition.

### Resuming a Half-Built Diagram

The `.excalidraw` file is the state of the build - a section-by-section diagram can be picked
up in a fresh session with no other context. To resume:

1. Read the `.excalidraw` file. The descriptive IDs and seed namespaces tell you which sections
   already exist (`trigger_*` with 100xxx seeds = section 1 done, and so on).
2. Render it and Read the PNG. What's on screen is what's built; what the plan called for and
   isn't there is what's left.
3. Check for dangling references before adding anything: `boundElements` entries and arrow
   `startBinding`/`endBinding` pointing at IDs that don't exist mean the previous session was
   interrupted mid-section - fix those first.
4. Continue from Phase 1 step 2 with the next section.

### Section Boundaries

Plan your sections around natural visual groupings from the diagram plan. A typical large diagram might split into:

- **Section 1**: Entry point / trigger
- **Section 2**: First decision or routing
- **Section 3**: Main content (hero section - may be the largest single section)
- **Section 4-N**: Remaining phases, outputs, etc.

Each section should be independently understandable: its elements, internal arrows, and any cross-references to adjacent sections.

### What NOT to Do

- **Don't generate the entire diagram in one response.** You will hit the output token limit and produce truncated, broken JSON. Even if the diagram is small enough to fit, splitting into sections produces better results.
- **Don't use a coding agent** to generate the JSON. The agent won't have sufficient context about the skill's rules, and the coordination overhead negates any benefit.
- **Don't write a Python generator script.** The templating and coordinate math seem helpful but introduce a layer of indirection that makes debugging harder. Hand-crafted JSON with descriptive IDs is more maintainable. This ban is repeated in the Render & Validate section below because it has been violated after being stated only here.

## Merging Multiple Sheets Into One

A C4 set, or any multi-sheet diagram, sometimes needs a single merged `.excalidraw` for
review or handoff - combining several **already-complete** files, each with its own id
space. This is not the section-by-section build above. Read
[references/merging-sheets.md](references/merging-sheets.md) before doing it: id
prefixing, rewriting every id reference (`containerId`, bindings, `boundElements`,
`groupIds`, `frameId`), shifting coordinates without rescaling, and dropping duplicate
legends. Do it via one `python3 - <<'EOF'` command, never a script file left on disk. It
isn't in `allowed-tools`, so it prompts for one-time approval like any ad-hoc Bash call -
expected, not a misconfiguration.

## Color as Meaning

Colors encode information, not decoration. Every color choice should come from [references/color-palette.md](references/color-palette.md) - the semantic shape colors, text hierarchy colors, and evidence artifact colors are all defined there.

**Key principles:**
- Each semantic purpose (start, end, decision, AI, error, etc.) has a specific fill/stroke pair
- Free-floating text uses color for hierarchy (titles, subtitles, details - each at a different level)
- Evidence artifacts (code snippets, JSON examples) use their own dark background + colored text scheme

**Do not invent new colors.** If a concept doesn't fit an existing semantic category, use Primary/Neutral or Secondary.

## Text Rules

**CRITICAL**: The JSON `text` property contains ONLY readable words.

```json
{
  "id": "myElement1",
  "text": "Start",
  "originalText": "Start"
}
```

Settings: `fontSize: 16`, `fontFamily: 3`, `textAlign: "center"`, `verticalAlign: "middle"`

## JSON Structure

```json
{
  "type": "excalidraw",
  "version": 2,
  "source": "https://excalidraw.com",
  "elements": [...],
  "appState": {
    "viewBackgroundColor": "#ffffff",
    "gridSize": 20
  },
  "files": {}
}
```

## Element Templates

See [references/element-templates.md](references/element-templates.md) for copy-paste JSON templates for each element type (text, line, dot, rectangle, arrow). Pull colors from [references/color-palette.md](references/color-palette.md) based on each element's semantic purpose.

**When the templates aren't enough** - you need a field they don't cover (container/text

name produces JSON that renders blank or throws in `exportToSvg`.

## Render & Validate (MANDATORY)

You cannot judge a diagram from JSON alone. After generating or editing the Excalidraw JSON, you MUST render it to PNG, view the image, and fix what you see - in a loop until it's right. This is a core part of the workflow, not a final check.

### How to Render

```bash
cd ${CLAUDE_SKILL_DIR}/references && uv run python render_excalidraw.py <path-to-file.excalidraw>
```

This outputs a PNG next to the `.excalidraw` file. Then use the **Read tool** on the PNG to actually view it.

The `.excalidraw` file and its PNG live side by side in the task's own working directory -
never in this skill's `references/` folder. The PNG is rebuilt from the source and must be
newer than it; if the two go stale relative to each other, re-render before showing
anything. Intermediate renders don't accumulate - only the current PNG needs to exist,
not a history of every iteration.

### The Loop

After generating the initial JSON, run this cycle:

**1. Render & View** - Run the render script, then Read the PNG.

**2. Audit against your original vision** - Before looking for bugs, compare the rendered result to what you designed in Steps 2-6. Ask:
- Does the visual structure match the conceptual structure you planned?
- Does each section use the pattern you intended (fan-out, convergence, timeline, etc.)?
- Does the eye flow through the diagram in the order you designed?
- Is the visual hierarchy correct - hero elements dominant, supporting elements smaller?
- For technical diagrams: are the evidence artifacts (code snippets, data examples) readable and properly placed?

**3. Check for visual defects:**
- Arrow direction is wrong: `startArrowhead`/`endArrowhead` decide what actually renders
  and can be inverted relative to the order of points in `points` - confirm direction by
  reading these two JSON fields, never by eye on the render. In one real session, 4 of 36
  arrows read backwards on the picture even though the JSON was internally consistent.
- Text clipped by or overflowing its container
- Text or shapes overlapping other elements
- Arrows crossing through elements instead of routing around them
- Arrows landing on the wrong element or pointing into empty space
- Labels floating ambiguously (not clearly anchored to what they describe)
- Uneven spacing between elements that should be evenly spaced
- Sections with too much whitespace next to sections that are too cramped
- Text too small to read at the rendered size
- Overall composition feels lopsided or unbalanced

**4. Fix** - Edit the JSON to address everything you found. Common fixes:
- Widen containers when text is clipped
- Adjust `x`/`y` coordinates to fix spacing and alignment
- Add intermediate waypoints to arrow `points` arrays to route around elements
- Reposition labels closer to the element they describe
- Resize elements to rebalance visual weight across sections

**5. Re-render & re-view** - Run the render script again and Read the new PNG.

**6. Repeat** - Keep cycling until the diagram passes both the vision check (Step 2) and the defect check (Step 3). Typically takes 2-4 iterations. Don't stop after one pass just because there are no critical bugs - if the composition could be better, improve it.

**7. Check the working directory** - Confirm no extra files appeared: no `.py` generator
script, no stray `.md` note, nothing beyond the `.excalidraw` and its PNG. The bans on
generator scripts and coding-agent delegation stated earlier are worth nothing if nobody
checks afterward - a past session violated both anyway, producing a script and a note
that nobody asked for. When this work is delegated to a subagent, repeat both bans
directly in its prompt - a subagent does not read the body of this skill and will not see
them otherwise.

Every completed iteration is a save point: the `.excalidraw` file is valid JSON that renders,
so an interrupted loop leaves a usable diagram rather than a broken one. If you have to stop
early, say which defects from Step 3 are still outstanding.

### When to Stop

The loop is done when:
- The rendered diagram matches the conceptual design from your planning steps
- No text is clipped, overlapping, or unreadable
- Arrows route cleanly, point the intended direction, and connect to the right elements
- Spacing is consistent and the composition is balanced
- The working directory has no stray files
- You'd be comfortable showing it to someone without caveats

### First-Time Setup
If the render script hasn't been set up yet:
```bash
cd ${CLAUDE_SKILL_DIR}/references && uv sync
cd ${CLAUDE_SKILL_DIR}/references && uv run playwright install chromium
```

`uv sync` generates `references/.venv/` on demand - it is not part of the skill bundle,
never checked in, and does not travel when the skill is copied to another machine or CPU
architecture; regenerate it there instead. If a `.venv` already exists and won't run
(wrong interpreter, broken symlinks), delete the directory and re-run `uv sync` rather

## Quality Checklist

For a System Block Model, walk the 8-item checklist at the end of
[references/system-block-model.md](references/system-block-model.md) **first** - element
budget, container heights, cross-cutting frame, one meaning per colour. A diagram that fails
it is rebuilt, not patched.

For a C4 set, walk the coverage table in
[references/c4-model.md](references/c4-model.md) first - every connection from the source
registry (Design Process, Step 3) must land on at least one sheet.

Before telling the user the diagram is done, read [references/quality-checklist.md](references/quality-checklist.md) and walk
its items, scored critical / major / minor. Items 21-27 are answerable only from the rendered PNG, so run the checklist
after the render loop has converged, not instead of it.
