# review - самообучающийся оркестратор код-ревью

Это НЕ отдельный движок правил. Правила ревью берутся из готового `mattpocock-skills:code-review`.
Ценность этого скилла - **обогащение вокруг него**: контекст задачи, конвенции репо, накопленный
персональный опыт по репо/модулю, постинг под именем пользователя в его тоне, и **самообучение**
после ручного ревью человека. Опыт подгружается **по запросу** через индекс - не грузи всю базу
знаний сразу.

**Режим (спроси на старте, AskUserQuestion):**
- **Полный** - 4-стадийный цикл с пользователем: черновик → пользователь отмечает `[x]` → постинг
  одобренного → ручное ревью человека → самообучение. Шаги 0→1→2→3→4.
- **Короткий (авто)** - без ревью человека: сам ревьюю, сам отбираю high-signal находки и **пуляю их
  в MR/PR** под именем пользователя, затем самообучение - по мере появления ответов. Шаги 0→1→2(авто)→4.

В обоих режимах в конце шага 1 черновик проходит через **судью** - независимый субагент,
перепроверяющий каждую находку против кода/CI/тикета и правящий её текст (детали -
[references/judge.md](references/judge.md)). В Коротком режиме это единственный факт-чекинг перед
автопостингом под именем пользователя, поэтому пропускать его там нельзя.

Технически 5 шагов - шаг 0 это подготовка контекста; дальше считаем шагами 0-4.

**Модели:** ревью-подсессия (шаг 1) идёт на Opus 5.5 (high/xhigh), оркестрация - на Sonnet 5; детали
в [references/review-engine.md](references/review-engine.md).

**Run-state (кратко):** run-директория -
`$REVIEW_RUNS_DIR/<host>-<repo>-<mr>-<ts>/` (по умолчанию `REVIEW_RUNS_DIR=~/.claude/review-runs`);
`state.json` хранит `step_completed`; на старте просканируй эту базу на резюмируемый прогон для
того же MR и предложи продолжить; чекпоинт после каждого шага. Полная схема - в
[references/run-state.md](references/run-state.md).

**Права и временные файлы (ВАЖНО, чтобы не спамить запросами прав):** run-дир лежит вне проекта,
прямой `Write`/redirect в неё запрашивает права на каждый файл. Поэтому: промежуточные файлы пиши в
**scratchpad сессии** (авто-разрешён; в редиректах - литеральный путь, не переменная), а в run-дир
переноси готовый артефакт **только** через `run_dir.sh stage/meta/create`. Никаких `python3`/ручного
`jq`/`cat >` в run-дир. Детали - [run-state.md](references/run-state.md) §1a.

**Форма вызова скриптов - строго одна** (под неё заведены allow-rules, иначе спросит права):
вызывай **по абсолютному пути, прямым запуском, без `bash` и без `~`**:
`~/.claude/skills/review/scripts/<name>.sh <args>`
(скрипты исполняемые). Не смешивай формы `bash …`/`~/…`/relative - они не сматчатся с правилом.
Нужные записи в глобальном `~/.claude/settings.json` (`permissions.allow`), по одной на скрипт:
`Bash(~/.claude/skills/review/scripts/run_dir.sh:*)`,
`… /glab_post_inline.sh:*)`, `… /fetch_author_comments.sh:*)`. Для опциональной задачи-напоминания
в Todoist - `Bash(td:*)` (если `td` зовётся абсолютным путём, нужна отдельная запись под этот путь:
правило по имени его не покрывает). Плюс `permissions.additionalDirectories: ["~/go"]` для чтения
GOMODCACHE (Go-репо).

**Доменная база проекта.** Ревью идёт в worktree другого репо, поэтому project-настройки того
каталога, откуда обычно работает пользователь, там не действуют - правила для инструмента доменной
базы (для qmd: `Bash(qmd search:*)`, `qmd query`, `qmd get`, `qmd multi-get`, `qmd update`,
`qmd embed:*`; плюс `Bash(modernize:*)` и др.) заводи в **глобальном** `~/.claude/settings.json`, а
каталог исходников базы открой через `additionalDirectories` - иначе правка файла базы на шаге 4
спросит права. Команды держи простыми, без цепочек через `&&` и без подстановки переменных (кроме
штатной переиндексации вроде `qmd update && qmd embed -c <коллекция>`). Адрес базы и рецепты
поиска/записи для каждого репо - в `knowledge-sources.md`.

## Две базы знаний - не смешивать

**Доменная база проекта** (внешняя, у каждого репо своя - см. `knowledge-sources.md`) хранит
*как система работает*: контракты, флоу, поведение кода, расхождения доки с кодом. Например,
qmd-коллекция над каталогом заметок проекта; как в неё ходить - задаётся записью репо в
`knowledge-sources.md`.

**Ревью-база скилла** (`knowledge/**` здесь) хранит *как ревьюить*: тон и стилистику комментов,
конвенции репо, минорные придирки, спорное/не-блокеры, мета «на что человек ловит чаще ИИ».

- **Чтение:** на шаге 0 подтягиваем обе - доменную по затронутым модулям, ревью-базу по INDEX.
- **Запись (шаг 4):** факт «как это работает» → **в доменную базу** (формат и переиндексация - по её
  записи в `knowledge-sources.md`); правило ревью и стилистика → **в ревью-базу**. Урок с обоими -
  факт в доменную, в ревью-базе только строка «проверять X, детали - <ссылка>».
- **Иерархия источников:** код > доменная база > внешняя документация (Confluence/`DOCS.md` и т.п.).
  Доменная база противоречит коду - верим коду и правим базу.

## Роли файлов (читай по запросу, не всё сразу)

- `INDEX.md` - карта опыта ревью `host → repo → подчасть → module → файл + триггеры`.
- `task-sources.md` - мапа `host+repo → источник задач`.
- `knowledge-sources.md` - мапа `host+repo → доменная база знаний проекта` (как в неё искать, как
  дополнять, её место в иерархии источников).
- [references/task-context.md](references/task-context.md) - сбор diff, тикета (Spec) и
  `CLAUDE.md`-конвенций (Standards).
- [references/review-engine.md](references/review-engine.md) - вызов `mattpocock-skills:code-review` в
  подсессии, обогащение/мёрж находок, модели.
- [references/judge.md](references/judge.md) - независимая верификация смёрженного черновика перед
  показом/постингом: свежий субагент, вердикты CONFIRMED/CORRECTED/SEVERITY-CHANGED/REJECTED,
  `judge-notes.md`.
- [references/hosts.md](references/hosts.md) - рецепты `glab`/`gh`: diff, постинг, сбор комментов автора.
- [references/run-state.md](references/run-state.md) - полная схема run-директории и `state.json`.
- [references/self-learning.md](references/self-learning.md) - дистилляция урока, **маршрутизация
  между доменной базой и ревью-базой**, обновление `knowledge/**`, `INDEX.md`, тона, мап
  `task-sources.md`/`knowledge-sources.md`.
- [references/simplification-patterns.md](references/simplification-patterns.md) - прогон
  `modernize` и паттерны упрощения (читает ревью-подсессия).
- База знаний скилла (**ревью-база**):
  - [`knowledge/_tone.md`](knowledge/_tone.md) - **общий голос пользователя** для комментов во всех
    репо: стиль, запреты, формы вопросов, длина, исключения (всегда грузить);
  - дерево `knowledge/<host>/<repo>/`, структура **своя у каждого репо**, растёт самообучением:
    - `_repo.md` - common-sense по репо + **как в этом репо организованы знания и правила
      self-learning** (всегда грузить, если есть);
    - `_tone.md` - (опц.) **поправки** к общему тону, подтверждённые на этом репо (жаргон команды,
      исключения из общих запретов); грузить вместе с общим, при конфликте побеждает репо-файл;
    - `<подчасть>/<module>.md` - специфика части репо (для монорепо это, например, `providers/<x>/…`;
      для микросервиса - домен/пакет); грузить только затронутые части;
  - конкретную раскладку и promotion общего знания держат `_repo.md` этого репо + `INDEX.md`.

На старте база пустая: есть только общий `knowledge/_tone.md` и шаблоны `INDEX.md`/мап. Всё
остальное появляется на шаге 4.

Пути `references/**`, `knowledge/**`, `INDEX.md`, `task-sources.md`, `knowledge-sources.md`
относительны корню скилла (`~/.claude/skills/review/`); run-директории живут отдельно в
`$REVIEW_RUNS_DIR` (по умолчанию `~/.claude/review-runs/`); доменная база - вообще вне
скилла (адреса - в `knowledge-sources.md`).

## Воркфлоу

### Шаг 0 - контекст
1. **Спроси режим** (AskUserQuestion): Полный или Короткий (авто) - см. блок «Режим» выше.
2. Определи `host`/`repo` (`git remote get-url origin` - отдельной командой, не в цепочке с `ls`).
   Просканируй незавершённый прогон **через** `scripts/run_dir.sh resolve <host> <repo> <mr>` (не `ls`
   руками) - если нашёлся, предложи продолжить с шага из `state.json`. Иначе заведи прогон:
   `scripts/run_dir.sh create <host> <repo> <mr>` (он засеет `state.json`).
3. Прочитай `references/task-context.md` и следуй ему: найди MR/PR (или фолбэк на локальный
   `git diff <base>...HEAD`), собери diff-summary, по `task-sources.md` вытяни тикет → **Spec** (если
   пары host+repo нет в мапе - спроси у пользователя источник и правило id, затем допиши запись),
   собери `CLAUDE.md` (корень + рядом с изменёнными файлами) → **Standards**.
4. Прочитай `INDEX.md`. Определи затронутые **подчасти** репо (по раскладке из его `_repo.md`,
   например `providers/<x>/…` в монорепо) и модули из путей диффа; подгрузи `knowledge/_tone.md`
   (всегда), `_repo.md` + `_tone.md` репо (если есть) и только совпавшие `<подчасть>/<module>.md`.
5. Прочитай `knowledge-sources.md` для этого `host+repo` и подтяни из **доменной базы** то, что
   описывает затронутый диффом функционал (рецепт поиска - в записи репо; если у базы есть свой
   скилл-навигатор, вызови его перед нетривиальным поиском). Нужны не все файлы, а те, что задают
   ожидаемое поведение изменённого кода: контракты, флоу, кэш, обработка ошибок и т.п.
   В `context.md` положи выжимку + пути/адреса в базе (не полные тексты). Если пары `host+repo` нет
   в мапе - спроси про базу и допиши запись.
6. Собери `context.md` **в scratchpad**, проставь метаданные
   `scripts/run_dir.sh meta <dir> ticket <T> base <B> mode <full|short>`, затем перенеси артефакт:
   `scripts/run_dir.sh stage <dir> 0 <scratchpad>/context.md`.

### Шаг 1 - самостоятельное ревью (подсессия)
Следуй `references/review-engine.md`. По порядку:

1. Запусти подсессию с `mattpocock-skills:code-review`. Входы: fixed point + Spec + Standards +
   выжимка из доменной базы + путь к `references/simplification-patterns.md` - по нему подсессия
   дополнительно гоняет `modernize` и проходит дифф по паттернам упрощения. Дифф она тянет сама,
   в основной контекст он не попадает.
2. Обогати вернувшиеся находки опытом из `knowledge/**` и фактами доменной базы, сверяя их с кодом.
3. Наложи HIGH SIGNAL фильтр - у упрощений из него отдельное исключение (review-engine.md §3).
4. Дедуплицируй и смёржи в `draft-review.md` (**в scratchpad**) чекбокс-списком
   `- [ ] file:line - <severity> - <текст в тоне пользователя>`.
5. Прогони **судью** - следуй [references/judge.md](references/judge.md) целиком (независимость,
   вердикты, формат вывода, контракт возврата - детали там, не дублируем здесь).
6. Перенеси: `scripts/run_dir.sh stage <dir> 1 <scratchpad>/draft-review.md
   <scratchpad>/judge-notes.md`. Покажи пользователю уже проверенный судьёй черновик + сводку
   `Судья: подтвердил N, поправил M, сменил severity K, отклонил L`.
7. **(опционально) Заведи задачу-напоминание в Todoist** - если уведомления до пользователя не
   доходят (ни терминальный BEL, ни desktop), задача в Todoist - надёжный способ сообщить ему, что
   черновик ждёт разметки. Формат - см. «Задача-напоминание в Todoist» ниже. Шаг пропускается, если
   `td` нет в PATH или пользователь от напоминаний отказался.

### Шаг 2 - постинг
- **Полный режим:** пользователь отмечает `[x]` нужные пункты в `draft-review.md`. По
  `references/hosts.md` запости **все отмеченные разом** как inline-комменты под именем пользователя и
  в его тоне (`knowledge/_tone.md` + поправки репо). **Ничего не постим без явного `[x]`.**
- **Короткий (авто) режим:** ревью человека нет - единственный факт-чекинг перед этим постингом уже
  прошёл на шаге 1 (судья, `references/judge.md`). Отбери из уже проверенных судьёй находок
  прошедшие precision-слой (высокая уверенность; severity Critical/Minor - Suggestions не пуляем,
  чтобы не спамить MR), проставь им `[x]` и запости так же под именем пользователя и в тоне. Кратко
  покажи, что запостил.

Собери `posted.md` в scratchpad и перенеси: `scripts/run_dir.sh stage <dir> 2 <scratchpad>/posted.md`.
Если на шаге 1 заводилась задача-напоминание - закрой её (найди по маркеру, см. ниже): работа
человека на ней кончилась.

### Задача-напоминание в Todoist (опционально)

Нужна, только если уведомления до пользователя не доходят. Требует CLI `td` (todoist-rs) в PATH.
Если сессия запущена в окружении с урезанным PATH, зови `td` абсолютным путём (`command -v td`
покажет его) и заведи под этот путь отдельное allow-правило.

Создание (шаг 1):

```
td add "Ревью MR !<iid> <repo> (<TICKET>): отметить [x] в <путь к draft-review.md> - N находок, K Critical [<project_path>!<iid>]" -p "<проект>" -P 2 -d "today" -l <лейбл>
```

- `<проект>` и `<лейбл>` - плейсхолдеры, подставь свои (например лейбл `review`);
- маркер `[<project_path>!<iid>]` в конце обязателен - по нему задача потом находится;
- путь к черновику - относительно `$REVIEW_RUNS_DIR`;
- длинного тире в тексте не ставим, только дефис.

Поиск и закрытие (шаг 2, а также когда MR заапрувлен или уехал):

```
td list -l <лейбл> --json | jq -r '.tasks[] | select(.content | contains("<project_path>!<iid>")) | .id'
td done <id>
```

Перед созданием прогоняй тот же поиск: задача на этот MR уже есть - не плоди вторую, при
необходимости обнови текст через `td edit <id> -c "…"`.

### Шаг 3 - ручное ревью человеком (только полный режим)
Вне скилла: пользователь глазами дочитывает код и дописывает свои замечания прямо в MR/PR. Скилл
ждёт сигнала «собери мои комменты / дообучись». В коротком режиме шаг пропускается.

### Шаг 4 - сбор фидбэка и самообучение
В полном режиме - по комментам человека, когда они появились. В коротком режиме ждать нечего -
`judge-notes.md` с шага 1 уже готов сразу после постинга, начинай дистилляцию по нему не дожидаясь
ответов на запощенное (`references/self-learning.md` §1a); если ответы всё же придут позже -
досопоставь их туда же. Следуй `references/self-learning.md`: в полном режиме собери комменты
автора из MR/PR в scratchpad и перенеси (`scripts/run_dir.sh stage <dir> 4
<scratchpad>/human-comments.md`), сверь с `draft-review.md` и/или `judge-notes.md`, дистиллируй
уроки и **разведи их по двум базам** (факт «как работает» → доменная
база по `knowledge-sources.md` + переиндексация; правило ревью/стилистика → ревью-база по правилам
этого репо, см. его `_repo.md`), обнови триггеры в `INDEX.md`, тон (общий `knowledge/_tone.md` или
поправки в `_tone.md` репо - см. self-learning.md §5), при необходимости
`task-sources.md`/`knowledge-sources.md`. Ревью-база живёт внутри скилла
(`~/.claude/skills/review/`) - правки в неё разрешены. **Только после этого удали run-директорию.**

## Принципы

- Ленивая загрузка: сначала INDEX/мапа, потом только нужные файлы знаний.
- Опыт - обобщённый и атомарный, не про конкретный MR. Один урок - по месту (репо/модуль).
- Один факт - одна база: доменные факты не копируем в ревью-базу, правила ревью не пишем в доменную.
  Дублирование = расхождение через два прогона.
- Устройство системы не разбираем с нуля: сначала ищем в доменной базе, потом сверяем с кодом.
- Постинг - под именем пользователя (авторизованные `glab`/`gh`), в его тоне.
