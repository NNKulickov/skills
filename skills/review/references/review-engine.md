# review-engine - STEP 1: запуск ревью и обогащение

Этот файл описывает ШАГ 1 воркфлоу: получить «сырое» ревью через существующий
навык `mattpocock-skills:code-review`, затем **обогатить** и **слить** его результат с
накопленными знаниями по модулям. На выходе - `draft-review.md` в run-директории.

## Модели и эффорт

Не гоняй весь пайплайн на одной модели - раскладка по шагам:

| Часть пайплайна | Модель | Эффорт |
| --- | --- | --- |
| Оркестрация/механика (шаги 0, 2, 4; git/glab/jq, тикет, CLAUDE.md, run-dir) | **Sonnet 5** (задаётся `model:` команды) | low-medium |
| Ревью-подсессия (шаг 1, поиск багов) | **Opus 5.5** (параметр `model` у Agent) | high / xhigh для крупных диффов |
| Merge/дедуп/HIGH SIGNAL фильтр (шаг 1, downstream) | **Sonnet 5** | medium |
| Судья (шаг 1, пост-мёрдж верификация - `judge.md`) | **Opus 5.5**, отдельный свежий вызов Agent | high / xhigh, тот же класс, что ревью-подсессия |
| Постинг (шаг 2) | **Sonnet 5** | low |
| Self-learning дистилляция (шаг 4) | **Opus 5.5** или Sonnet 5 | medium |

**Принцип:** никогда не вешай «репорти только блокеры» на high-effort модель - это
худший случай для recall (сильная модель тратится на то, чтобы молчать). Сильную
модель ставим туда, где она ищет баги, а не туда, где она их отсеивает.

## 1. Вызов подсессии

Запусти подагента (Tool `Agent`, `subagent_type: general-purpose`) с
**`model: opus`** (Opus 5.5) на эффорте **high** - а для крупных или рискованных
диффов **xhigh**. Поиск багов - единственное место в пайплайне, где стоит держать
более сильную модель. Его единственная задача - вызвать навык
`mattpocock-skills:code-review` (через Tool `Skill`) и вернуть его находки. Подсессия
нужна, чтобы держать контекст текущей сессии чистым: сырой diff и промежуточные
рассуждения ревью не засоряют основную нить.

**Гигиена shell - передай подсессии ДОСЛОВНО (иначе она забьёт пользователя запросами прав).**
Пользователь обычно запускает ревью через `claude --worktree`, поэтому **cwd подсессии УЖЕ равен
каталогу цели** (worktree/чекаут ветки). Значит:

> - Гоняй git **прямо в cwd**, без `cd` и без абсолютных путей: `git diff --stat <BASE_REF>...HEAD`,
>   `git show <BASE_REF>:<относительный путь>`. НИКОГДА не делай `cd <dir> && git …` - песочница флагит
>   это как «выполнение хуков из чужого каталога» и спрашивает права на каждую команду.
> - Только если цель РЕАЛЬНО отличается от cwd - используй **`git -C <dir> …`** (git ведёт себя так,
>   будто запущен там, но без `cd`). Не подставляй абсолютный путь, который и так равен cwd.
> - Одна команда за раз. НЕ склеивай git с `echo`/`ls`/`tail`/`head`/`find` через `&&` - цепочка
>   теряет покрытие allow-list `git:*` и снова спрашивает права.
> - НЕ используй циклы `for f in …; do … "$f"; done` и любую подстановку переменных внутри команды -
>   песочница не может её проанализировать («simple_expansion»). Нужно несколько файлов - либо один
>   `git diff <BASE_REF>...HEAD -- <путь1> <путь2>` с **литеральными** путями, либо по одному
>   `git show <BASE_REF>:<литеральный путь>` на файл.
> - Полный diff бери одной командой `git diff <BASE_REF>...HEAD` (или `glab mr diff`/`gh pr diff`).
>   Временные файлы и редиректы в переменные не нужны.
> - Нужен поиск по коду (не по diff) - используй `Grep`/`Glob` (директория явным параметром) или
>   `grep -rn "pattern" --include="*.go" /абсолютный/путь`/`find /абсолютный/путь -name ...`.
>   НИКОГДА не `cd <dir> && grep -r ...`/`find ...` - та же связка "cd + рекурсивное чтение по
>   маске", тот же guard, тот же запрос прав на каждый вызов.

Передай подсессии `<BASE_REF>` явно и НЕ передавай `<TARGET_DIR>`, если он совпадает с cwd (обычный
случай `--worktree`) - иначе она начнёт `cd` в собственный cwd.

**Не поллить детей через shell.** Если подсессия сама порождает дочерние агенты (mattpocock внутри
разветвляется на Standards/Spec), она должна **дождаться их результатов штатно** - синхронными
вызовами Agent/Skill, результат которых возвращается по завершении. НИКАКИХ самодельных wait-циклов
вида `while …; do wc -c < $D/x.output; sleep 15; done`: подстановка переменных в таком цикле не
анализируется песочницей («simple_expansion») и на каждый заход спрашивает права. Не запускай детей в
фоне, чтобы потом опрашивать их output-файлы, - вызывай и жди результат напрямую.

**Coverage-first (слой recall).** В промпт подагента добавь явный блок: ревью-
подсессия должна **МАКСИМИЗИРОВАТЬ ПОКРЫТИЕ** - репортить ВСЁ, что вызывает
подозрение. Каждую находку помечай тегами `confidence: high|med|low` и
`severity: critical|minor|suggestion` плюс одна строка обоснования. Подсессия
**НЕ должна** заниматься самоцензурой: НИКАКОГО «при сомнении не флагать»,
НИКАКОГО «только блокеры». Это слой recall - его задача не пропустить реальный баг,
а не отфильтровать шум (фильтрация будет ниже, на слое precision, §3). Эта
инструкция **перекрывает** дефолтную консервативность `mattpocock-skills:code-review`
(«репортить только high-priority»): здесь, на шаге генерации, консервативность
отключаем.

Входные данные, которые передаём в промпт подагента:

- **Fixed point** - база сравнения (merge-base / base-ветка). Передавай явно, напр.
  `git merge-base HEAD <base>` или диапазон `<base>...HEAD` (или iid MR/PR). Ревьюим
  только то, что добавлено в этой ветке относительно фиксированной точки, не весь
  репозиторий. Полный diff подсессия **тянет сама** (`glab mr diff` / `gh pr diff` /
  `git diff <base>...HEAD`) - не передавай ей файл с диффом, чтобы не гонять его через
  основной контекст и не плодить временные файлы.
- **Spec source** - текст тикета, собранный на шаге 0. Вставляй его прямо в промпт
  (полный текст, не ссылку) - это источник истины про то, что код *должен* делать.
- **Standards sources** - пути к файлам `CLAUDE.md` репозитория (собраны на шаге 0),
  плюс короткие выдержки из нашей ревью-базы `knowledge/**`, релевантных затронутым
  модулям. Это источник истины про то, *как* код должен быть написан.
- **Domain context** - выжимка из доменной базы проекта (шаг 0, §5b task-context.md): как устроен
  затронутый функционал и чего от него ждут вызывающие. Вставляй выжимку в промпт, а рядом дай
  подсессии способ дочитать самой - коллекцию и команды из `../knowledge-sources.md` (для
  qmd-базы: `qmd search "<идентификатор>" -c <коллекция> -n 5`,
  `qmd get qmd://<коллекция>/<путь>`). Это источник истины про то, *как система работает*, и главный
  инструмент для находок класса «код формально корректен, но контракт другой». Правило для подсессии:
  **устройство системы сначала искать в доменной базе, а не выводить из диффа**; факт из базы,
  на который опирается находка, - проверить по её якорю в коде (база может отставать от кода).

- **Два прохода на упрощение** - путь к [simplification-patterns.md](simplification-patterns.md)
  и требование выполнить оба перед возвратом находок: прогон `modernize` по пакетам диффа с
  фильтром по новым строкам и проход по списку паттернов, которые инструмент не находит. Оба
  проходят по полному диффу, который подсессия и так тянет сама, - поэтому они здесь, а не в §3:
  в основную сессию дифф не попадает. Находки возвращай в том же формате, с тегами `confidence` и
  `severity` (шкала - в конце того файла).

Сам навык `mattpocock-skills:code-review` внутри разветвляется на два параллельных
подагента - **Standards** и **Spec** - и возвращает находки бок о бок. Мы этим
пользуемся: не переизобретаем ревью, а достраиваем его нашим слоем.

## 2. Fallback

Проверено: спавн-подагент **видит и может вызвать** `mattpocock-skills:code-review`
(изоляция контекста держится - это основной путь §1). Fallback нужен, только если в
конкретном окружении навык подагенту недоступен:

1. вызови `mattpocock-skills:code-review` в **текущей** сессии (контекст будет грязнее);
2. в крайнем случае примени встроенные правила ниже напрямую.

Важно: точное имя навыка - `mattpocock-skills:code-review` (префикс плагина
`mattpocock-skills`), не `mattpocock:code-review`.

## 3. Слой обогащения (наш) - downstream precision layer

Это **слой precision**: он работает над **полным списком кандидатов**, который
вернула ревью-подсессия (§1, слой recall), и именно здесь отсеивает шум,
дедуплицирует и накладывает знания. Важно: фильтрация (HIGH SIGNAL / отсев шума)
**НЕ должна** происходить на шаге генерации находок - только здесь, над полным
списком кандидатов. На шаге генерации мы собираем максимум подозрений, на этом
шаге - сжимаем их до доверенных.

Получив полный список находок mattpocock, наложи сверху:

- **Модульные проверки** из ревью-базы `knowledge/**` - подгружай их через INDEX, собранный на
  шаге 0 (только файлы, релевантные затронутым модулям).
- **Сверку с доменной базой** - каждую находку, которая опирается на «как система работает»,
  подтверждай либо фактом из доменной базы (с адресом в базе и якорем в коде), либо прямым чтением
  кода. Расхождение диффа с зафиксированным в базе контрактом - сильный сигнал (Critical/Minor);
  расхождение **базы с кодом** - не находка ревью, а материал для шага 4 (починить базу).
- **HIGH SIGNAL фильтр** - это и есть фильтр precision-слоя для подавления шума.
  Применяй его дословно, над полным списком кандидатов:

  > **CRITICAL: только HIGH SIGNAL находки.** Флагать, когда:
  > - код не скомпилируется/не распарсится (синтаксис, типы, отсутствующие импорты, неразрешённые ссылки)
  > - код гарантированно даёт неверный результат независимо от входов (явные логические ошибки)
  > - явное однозначное нарушение CLAUDE.md, где можно процитировать нарушенное правило
  > - пайплайн MR красный (см. task-context.md §2a): причина падения - находка №1, даже если это
  >   «всего лишь» стиль, потому что MR в таком виде не вмержат
  >
  > НЕ флагать:
  > - стиль или общие «quality» замечания
  > - потенциальные проблемы, зависящие от конкретных входов/состояния
  > - субъективные улучшения
  > - pre-existing проблемы
  > - то, что выглядит багом, но на деле корректно
  > - педантичные придирки, которые senior не стал бы отмечать
  > - то, что поймает линтер - **но только если линтер зелёный**; уже упавший линтер идёт в находки
  > - проблемы, упомянутые в CLAUDE.md, но явно заглушённые в коде (напр. lint-ignore)
  >
  > При сомнении - не флагать. False positives подрывают доверие.

  **Единственное исключение из «не флагать стиль и субъективные улучшения» - упрощения,
  которые вернула подсессия** (§1, последний вход её промпта). Пункт «то, что поймает линтер»
  их не покрывает: `modernize` в CI не гоняется, так что зелёный пайплайн про эти находки ничего
  не говорит. Прогон и проход по паттернам делает подсессия, у неё уже есть дифф; здесь ты только
  раскладываешь результат по severity - шкала в конце
  [simplification-patterns.md](simplification-patterns.md), и ни одно упрощение само по себе не
  переводит вердикт в `CHANGES_REQUESTED`.
- **Два правила из монорепо-ревьюера** (портирование конвенций):
  - **Проверяй поведение сторонних библиотек по исходникам.** Не доверяй
    комментариям и памяти - читай установленный исходник в `go env GOMODCACHE`
    (путь к конкретной версии из `go.mod`), чтобы убедиться, что вызов ведёт себя
    так, как предполагает изменение. GOMODCACHE лежит **вне workspace** (`~/go/...`),
    поэтому доступ к нему требует `permissions.additionalDirectories: ["~/go"]` в
    `settings.json` - иначе `grep`/чтение исходников будет спрашивать права. Команды
    держи простыми (`grep -rn "<pattern>" <файл>`), без `2>/dev/null`-редиректов и
    цепочек - чтобы попадать под allow-list `grep:*`.
  - **Сравнивай изменение с соседними модулями.** Смотри, как ту же задачу
    решают sibling-модули в монорепо (соседние плагины, адаптеры, интеграции), и сверяй конвенции (структуру, именование,
    обработку ошибок) с ними, а не выдумывай новые.

## 4. Формат черновика

Слей всё воедино (**дедуплицируй** пересечения между находками mattpocock и нашим
слоем - одна и та же проблема не должна попасть дважды) в `draft-review.md` внутри
run-директории. Формат - чеклист из чекбоксов:

```
- [ ] file:line - <severity> - <текст>
```

Severity-корзины:

- **Critical** - блокирует merge;
- **Minor** - желательно поправить;
- **Suggestions** - опционально.

Группируй находки по severity (сначала Critical, затем Minor, затем Suggestions).

Текст каждой находки пиши **в тоне пользователя** - перед составлением черновика
прочитай общий `knowledge/_tone.md` и поправки к нему из `knowledge/<host>/<repo>/_tone.md`, если
такой есть (при конфликте побеждает репо-файл), и следуй им (формулировки, обращение, уровень
категоричности).

Заверши черновик отдельной строкой вердикта:

```
VERDICT: APPROVED | CHANGES_REQUESTED
```

## 5. Требования к находкам

- Каждая находка обязана указывать конкретный `file:line`.
- `line` - та строка, **где читатель диффа увидит проблему по ходу чтения**, а не где сущность
  объявлена: дублирование хелпера цепляем к месту вызова, а не к определению функции. Коммент вне
  потока чтения человек переставляет вручную (на практике: черновик дал `:346`, человек запостил на `:55`).
- Для каждой **Critical** находки добавляй одну строку сценария отказа - как именно
  и при каких условиях код сломается (напр. «при пустом slice - index out of range»).
