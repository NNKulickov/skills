# STEP 0 - Сборка контекста ревью

Цель шага: собрать три вещи для полноценного ревью и записать их в `context.md`
(см. `run-state.md`): **Diff** (что изменилось), **Spec** (тикет/описание - зачем),
**Standards** (конвенции репо - как принято). Плюс подтянуть накопленные знания.

> **Права / гигиена shell.** Пользователь запускает ревью через `claude --worktree`, поэтому cwd УЖЕ
> равен каталогу ветки/worktree. Промежуточные файлы (в т.ч. `context.md` и любые сохранённые диффы)
> пиши в scratchpad сессии; в run-дир переноси только `scripts/run_dir.sh stage`. Правила, чтобы
> песочница не спрашивала права на каждую команду:
> - Гоняй git **прямо в cwd** без `cd` и абсолютных путей (`git diff --stat <base>...HEAD`). НИКОГДА
>   `cd <dir> && git …` - флагится как «выполнение хуков из чужого каталога».
> - `git -C <dir> …` - только если цель реально отличается от cwd; не подставляй путь, равный cwd.
> - Одна команда за раз; не склеивай через `&&` с `ls`/`head`/`wc`/`echo`/`find` (теряется `git:*`).
> - Не используй циклы `for/while` с `$var` и подстановку переменных внутри команды - не анализируется
>   («simple_expansion»); передавай **литеральные** пути.
> - В редиректах - литеральный путь scratchpad, не переменную (`> $VAR/x` спрашивает права).
> Подробности - run-state.md §1a.

## 1. Определение хоста и репо

```
git remote get-url origin
```
(Отдельной командой - не `git ... && ls <база прогонов>`: цепочка с `ls`/`head` не покрыта
allow-list и спросит права. Сканирование прогонов делает `scripts/run_dir.sh resolve`.)

Разбор URL:
- `gitlab.*` в хосте → работаем через `glab`;
- `github.com` → через `gh`.

Извлекаем path репо (например `group/project`) из URL
(`git@gitlab.example.com:group/project.git` или `https://.../group/project.git`).

Внимание: у GitLab-репо может быть несколько remote'ов, и fetch/push URL у `origin`
могут отличаться. Берём именно **fetch URL** `origin` (`git remote get-url origin` без
`--push`).

## 2. Поиск MR / PR

**GitLab:**
```
glab mr list --source-branch <branch>     # найти IID
glab mr view <iid>                         # title / author / state
glab mr diff <iid>                         # unified diff
```

**GitHub:**
```
gh pr list --head <branch>
gh pr view <n>
gh pr diff <n>
```

## 2a. Статус пайплайна - до чтения диффа

Красный CI - не «стиль, который поймает линтер», а факт: в таком виде MR не вмержат. Смотрим
**до** разбора диффа и пишем в `context.md` одной строкой (пайплайн + вердикт):

```
glab api "projects/<url-encoded-path>/merge_requests/<iid>"    # head_pipeline: status + sha
glab api "projects/<project-id>/pipelines/<pipeline-id>/jobs"  # какой джоб упал
glab api "projects/<project-id>/jobs/<job-id>/trace"           # причина падения
```

Если статус `failed` - причина падения становится находкой №1 в черновике (см. HIGH SIGNAL в
`review-engine.md`): имя джоба, правило или упавший тест, цитата из трейса. Пайплайн `running` -
отмечаем как «на момент ревью не завершён», это не находка.

Частый случай - линт-джоб с приватным плагином: замечания стиля, которые локально никто не
прогнал, потому что считалось, что плагин нельзя запустить вне CI. Если в проекте есть способ
запустить его локально (скрипт, make-цель, отдельный скилл) - сошлись на него в находке.

**Fallback (MR/PR ещё не создан):** ревьюим локальный diff.
База - целевая ветка (epic/master или та, что назвал пользователь):
```
git merge-base <base> HEAD
git diff <base>...HEAD          # three-dot: изменения ветки с точки расхождения
```
Три точки (`...`) дают diff относительно merge-base - это и есть скоуп ветки,
без посторонних изменений базы. Если пользователь назвал базовую ветку - используем её,
иначе пробуем epic-ветку, затем `master`/`main`.

**Оркестратору хватает summary диффа**, не тащи полный текст в основной контекст: возьми
`git diff --stat <base>...HEAD` (или `--name-only`) - он мал, кладётся в `context.md` инлайн без
файла и редиректа. **Полный** diff тянет ревью-подсессия сама (шаг 1, см. review-engine.md) -
передаём ей fixed point (`<base>...HEAD` / iid), а не файл с диффом. Если полный diff всё же нужно
сохранить (крупный, шарим между шагами) - пиши в scratchpad по **литеральному** пути, не в `$VAR`.

Конкретные рецепты для diff/view/постинга - в `hosts.md`.

## 3. Тикет (Spec)

Источник тикета зависит от хоста+репо. Читаем карту `../task-sources.md`:

1. Находим запись для текущего `host + repo`.
2. Применяем её `id_rule` (regex по имени ветки / заголовку MR) - извлекаем id тикета.
3. По `type` записи получаем тикет (`fetch`):
   - **youtrack**: id вида `PROJ-123`, `mcp__youtrack__get_issue` с этим id, при необходимости
     `mcp__youtrack__get_issue_comments` (или другой рецепт из поля `fetch`);
   - **jira** / **linear**: по рецепту `fetch` записи (MCP или CLI);
   - **github-issues**: `gh issue view <n>`;
   - **none**: тикета нет - как Spec используем описание самого MR/PR.

**Если пары host+repo нет в карте** - СПРОСИТЬ пользователя: тип источника и правило
извлечения id. Затем дописать новую запись в `task-sources.md` (append, не трогая
существующие).

### 3a. Аттачменты тикета - вытаскивать ВСЕ, до начала ревью

Аттачи (JSONSchema, XSD, сэмплы, PDF/xlsx спеки внешнего API) - первоисточник, он выше нашей
спеки и кода. Тикет без прочитанных аттачей - неполный Spec.

- Список аттачей снимать всегда (трекер обычно отдаёт его вместе с тикетом) и фиксировать
  в `context.md`, включая непрочитанные.
- Читать **до** формирования находок.
- Не удалось скачать/распаковать (`.zip`/`.rar`, бинарь, нет доступа) - **попросить файлы
  у пользователя**, он предоставит (обычно кладёт в `~/Downloads/<тикет>/`). Вслепую не ревьюить.

Без первоисточника находка по спеке - гипотеза. На одной XML→JSON миграции шесть Critical по типам
полей оказались ложными: спека автора дословно воспроизводила схему внешнего API.

Когда схема на руках:

- **Схема внешнего API бывает несогласована сама с собой** - одно имя поля с разными типами
  в разных определениях чаще означает два разных поля, а не баг автора. «Один из двух типов
  точно неверен» без сверки - невалидный вывод.
- **Отсутствие ограничений - тоже факт:** `{"type": "string"}` без `pattern` (типично для
  `xs:dateTime`) = формат не гарантирован, и жёсткий парсер по паре форматов - реальная находка.
- `required` + `minItems` закрывают класс гипотез «а если придёт пусто».
- Прогнать по схеме **все** места, где конвертер закладывается на тип (`strconv.Itoa`, касты):
  промах роняет разбор всего ответа, включая неиспользуемые поля (если JSON-парсер строгий).

## 4. Конвенции (Standards)

Собираем все релевантные `CLAUDE.md`:

```
git diff --name-only <base>...HEAD          # или через glab/gh - список изменённых файлов
```

- корневой `CLAUDE.md` репозитория;
- любой `CLAUDE.md` в директориях по пути изменённых файлов - идём вверх (walk up) от
  каждого изменённого файла до корня репо и проверяем наличие `CLAUDE.md` в каждой
  промежуточной директории (`find` / прямая проверка пути).

Собранные пути передаём как Standards-источники (отмечаем факт их наличия).
Если ни одного `CLAUDE.md` нет - так и указываем в `context.md`.

## 5. Загрузка знаний - из двух баз

### 5a. Ревью-база скилла (как ревьюить)

Всегда грузим общий тон `knowledge/_tone.md`. По изменённым модулям сверяемся с `../INDEX.md` и
подгружаем подходящие файлы `knowledge/<host>/<repo>/**` (поправки к тону, конвенции репо, мета «на
что смотреть»). Механика описана в `SKILL.md`.

### 5b. Доменная база проекта (как система работает)

Читаем `../knowledge-sources.md`, находим запись для текущего `host + repo` и подтягиваем из
доменной базы описание затронутого диффом функционала. Для базы типа `qmd`:

1. если в записи указан скилл-навигатор по базе (поле `skill`) - вызови его (Tool `Skill`): в нём
   синтаксис поиска, словарь терминов и карта разделов; не угадывай запросы сам;
2. ищи по коллекции из записи - точные идентификаторы через `qmd search`, концептуальные
   вопросы через `qmd query`;
3. найденное забирай целиком (`qmd get`), а не по сниппетам.

Для других типов (`files`, `confluence`) - по рецепту `read` записи.

Что искать - то, что задаёт **ожидаемое поведение изменённого кода**: контракты API и этапов
обработки, ограничения и фича-флаги, кэш и его ключи, флоу записи/чтения, обработка ошибок,
пайплайны данных - по тому, что реально затронул дифф. Если пары `host+repo` нет в мапе - спросить пользователя про базу и дописать запись.

**Приоритет:** код > доменная база > внешняя дока (Confluence/`DOCS.md` и т.п.). Факт из базы, на который опирается
находка ревью, проверяй по указанному в базе якорю (`repo/path.go:NN`) - база может отставать от кода;
если отстала, это материал для шага 4 (починить базу).

В `context.md` кладём **выжимку + адреса в базе** (для qmd - `qmd://`-пути), не полные тексты файлов.

## 6. Выход шага

Всё собранное - host/CLI, IID/номер, diff-summary, Spec (тикет или описание), список
Standards-путей, подгруженные файлы ревью-базы, выжимка из доменной базы с адресами -
оформляем в `context.md` **в scratchpad**, затем
переносим в run-дир: `scripts/run_dir.sh stage <dir> 0 <scratchpad>/context.md` (метаданные тикета/
базы/режима - `run_dir.sh meta`). Структура - в `run-state.md`. Это вход для последующих шагов ревью.
